## 1. Overview & Hardware Mental Model

Modern CPUs do not execute instructions directly against main RAM. Instead, each CPU core possesses private hardware L1 and L2 caches, plus a shared L3 cache. 

:::tip Engineering Mental Model
Multi-threaded concurrency bugs in Java stem from two hardware optimizations:
1. **CPU Caching & Visibility**: Core 1 modifies a variable in its L1 cache; Core 2 reads from its own stale L1 cache and never sees the change.
2. **Instruction Reordering & Speculative Execution**: The Java compiler (JIT) and CPU reorder independent instructions to maximize instruction pipeline efficiency, breaking sequential assumptions across threads.
:::

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                          HARDWARE CPU CACHE HIERARCHY                       │
```

## 2. The Java Memory Model & Happens-Before Semantics

The **Java Memory Model (JMM, JSR-133)** defines the rules governing when writes by one thread are guaranteed to be visible to reads by another thread.

### The Happens-Before Relationship
If Action `A` *happens-before* Action `B` (`A happens-before B`), the memory effects of Action `A` are guaranteed to be visible to Action `B`.

Key JMM Happens-Before Rules:
1. **Program Order Rule**: Each action in a single thread happens-before every action that comes later in the program order of that thread.
2. **Monitor Lock Rule**: An unlock on a monitor lock happens-before every subsequent lock on that same monitor lock.
3. **Volatile Variable Rule**: A write to a `volatile` field happens-before every subsequent read of that same `volatile` field.
4. **Thread Start Rule**: A call to `Thread.start()` happens-before any action in the started thread.
5. **Thread Join Rule**: All actions in a thread happen-before any other thread successfully returns from `Thread.join()` on that thread.
6. **Transitivity**: If `A happens-before B` and `B happens-before C`, then `A happens-before C`.

## 3. The `volatile` Keyword & Memory Barriers

Declaring a field `volatile` instructs the JVM and JIT compiler:
1. **Never cache** the variable in CPU registers or thread-local caches; always read directly from main memory.
2. **Never reorder** memory operations around the volatile access by inserting CPU **Memory Barriers** (Fences):
   - `StoreStore` and `StoreLoad` barriers on volatile writes.
   - `LoadLoad` and `LoadStore` barriers on volatile reads.

```java
// CLASSIC TRAP: Volatile is NOT sufficient for compound atomic operations!
public class Counter {
    private volatile int count = 0;

    public void increment() {
        count++; // THREE BYTECODES: getfield -> iadd -> putfield (RACE CONDITION!)
    }
}
```

<Aside type="danger" title="Why volatile count++ is NOT Thread-Safe">
`count++` is not a single atomic operation. It consists of: (1) read value, (2) add 1, (3) write value back. If two threads execute `count++` concurrently, both read `5`, both calculate `6`, and both write `6` back, losing one update!
**Solution**: Use `AtomicInteger.incrementAndGet()` (Lock-free hardware CAS) or `synchronized`.
</Aside>

## 4. `synchronized` & HotSpot Monitor Lock Inflation

In Java, every object can act as a synchronization monitor. The HotSpot JVM implements an adaptive multi-tier locking strategy:

```
┌─────────────────┐       Under Contention        ┌─────────────────────┐
│  Biased Lock    │ ────────────────────────────> │  Lightweight Lock   │
│ (Zero CAS cost; │                               │ (CAS spin lock in   │
│  Thread ID in   │                               │  thread stack frame)│
│  Mark Word)     │                               └──────────┬──────────┘
└─────────────────┘                                          │
                                                             │ High Contention
                                                             ▼ (Thread Blocks)
                                                  ┌─────────────────────┐
                                                  │  Heavyweight Lock   │
                                                  │ (OS Mutex / Parker  │
                                                  │  Kernel Context Sw) │
                                                  └─────────────────────┘
```

1. **Biased Locking** (Legacy/Deprecated in JDK 15): Assumes lock is acquired by only one thread. Writes Thread ID directly into object Mark Word.
2. **Lightweight Locking**: When multiple threads contend without blocking, threads use CPU CAS (Compare-And-Swap) instructions to spin-wait without context-switching to the OS kernel.
3. **Heavyweight Locking**: When spin threshold is exceeded, the JVM inflates the lock into an OS-level Mutex (`ObjectMonitor`). Contending threads are parked (`pthread_mutex_lock`), incurring expensive OS context-switching costs (~1–3 microseconds).

## 5. `ReentrantLock` & AbstractQueuedSynchronizer (AQS)

`java.util.concurrent.locks.ReentrantLock` provides explicit locking capabilities beyond `synchronized`:
- **Timed Lock Acquisition**: `tryLock(5, TimeUnit.SECONDS)` prevents indefinite deadlocks.
- **Interruptible Locks**: `lockInterruptibly()` responds to thread interruption.
- **Fairness Policy**: Optional FIFO queue ordering (`new ReentrantLock(true)`).
- **Multiple Condition Variables**: Allows granular signaling via `lock.newCondition()`.

```java
// Production Idiom for ReentrantLock
private final ReentrantLock lock = new ReentrantLock();

public void performCriticalAction() {
    lock.lock();
    try {
        // Critical section modifying shared mutable state
    } finally {
        lock.unlock(); // ALWAYS unlock in finally block!
    }
}
```

## 6. `ThreadPoolExecutor` Architecture & Production Sizing

```java
public ThreadPoolExecutor(
    int corePoolSize,
    int maximumPoolSize,
    long keepAliveTime,
    TimeUnit unit,
    BlockingQueue<Runnable> workQueue,
    ThreadFactory threadFactory,
    RejectedExecutionHandler handler
)
```

```
                     THREAD POOL TASK PROCESSING FLOW
Task Arrives ──> Active Threads < corePoolSize? ──YES──> Spawn New Core Thread
                          │ NO
                          ▼
                 workQueue.offer(task)? ─────────YES──> Enqueue Task in Buffer
                          │ NO (Queue Full)
                          ▼
                 Active Threads < maximumPoolSize? ──YES──> Spawn Non-Core Thread
                          │ NO (Pool & Queue Saturated)
                          ▼
                 Trigger RejectedExecutionHandler (AbortPolicy, CallerRunsPolicy)
```

### Production Thread Pool Sizing Formulas (Brian Goetz)
- **CPU-Bound Tasks** (Heavy computation, hashing, encryption):
  `Optimal Threads = N_cpu + 1`
- **I/O-Bound Tasks** (Database queries, external REST API calls, disk reads):
  `Optimal Threads = N_cpu * (1 + W / C)`
  *(where W is wait time on I/O and `C` is CPU computation time)*.

<Aside type="caution" title="Production Trap: Executors.newFixedThreadPool()">
`Executors.newFixedThreadPool(n)` uses an **unbounded `LinkedBlockingQueue`** with capacity 2^{31}-1. If downstream services slow down, incoming requests queue indefinitely in RAM until the JVM crashes with `java.lang.OutOfMemoryError: Java heap space`.
**Rule**: Always construct `ThreadPoolExecutor` directly with a **bounded queue** (e.g. `ArrayBlockingQueue(500)`) and a `CallerRunsPolicy` or metrics-backed rejection handler.
</Aside>

## 7. Java 21 Virtual Threads (Project Loom)

Java 21 introduces **Virtual Threads** (`Thread.ofVirtual().start(...)`):
- Lightweight user-mode threads managed by the JVM rather than 1:1 OS kernel threads.
- Stack memory scales dynamically (few hundred bytes vs 1 MB OS thread stack).
- When a Virtual Thread blocks on network/file I/O, the JVM **unmounts** it from the underlying carrier OS thread and mounts another runnable virtual thread, enabling **millions of concurrent connections** without reactive programming complexity.
